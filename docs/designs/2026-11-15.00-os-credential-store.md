# OS credential store

## Status and scope

Implemented in `dm-credentials` and wired into Tauri startup. Replaces the plaintext
`credentials/vault.json` as the default credential storage on every desktop target
(macOS, Windows, Linux). Account passwords and remembered DLsite sessions are covered;
nothing else moves out of SQLite or the managed content files.

## Goal and constraints

- Keep account secrets in the operating system's credential store instead of a
  plaintext file protected only by file permissions.
- Keep platform-specific code out of this repository. All per-OS selection lives in the
  `keyring` crate (4.x, `v1` feature): macOS Keychain, Windows Credential Manager, and
  the freedesktop Secret Service on Linux/BSD.
- Linux must work on the major desktops. The Secret Service API is provided by GNOME
  Keyring (GNOME, Cinnamon, MATE, Xfce, Budgie), KWallet (KDE Plasma; since KF 5.97),
  and KeePassXC. The zbus-based store unlocks a locked collection through the desktop's
  own prompt and creates the default collection when it is missing.
- Remembered sessions are about 4 KiB of cookie JSON. Windows Credential Manager rejects
  blobs over 2560 bytes (`CRED_MAX_CREDENTIAL_BLOB_SIZE`), so secrets cannot be stored
  one per OS entry without per-platform chunking.

## Design

Envelope encryption with a single OS entry:

- The OS store holds one random 32-byte vault key: service = Tauri app identifier,
  user = `credential-vault-key`. The QA build's distinct identifier therefore gets its
  own key.
- `credentials/vault.sealed` holds the existing `{ "passwords": { ref: secret } }` JSON,
  encrypted with XChaCha20-Poly1305 (random 24-byte nonce per write). File layout:
  `DMVAULT1` magic, nonce, ciphertext; the magic is the AEAD associated data. Writes are
  temp-file + rename with private permissions, as before.
- The key is read lazily on the first credential operation and cached for the process,
  so there is at most one OS access/unlock prompt per run.
- XChaCha20-Poly1305 (RustCrypto, pure Rust) was chosen over the already-linked AWS-LC
  so `dm-credentials` can be compile-checked for every target from any host and needs no
  C toolchain.
- On Linux the zbus Secret Service client is pure Rust; no new system libraries are
  linked.

`CredentialStore` is unchanged; `open_credential_store(dir, identifier)` selects the
store and reports the backend:

1. `vault.sealed` exists: always use the sealed store. If the OS store is unavailable,
   credential operations fail with `CredentialsError::Os` instead of silently
   downgrading to plaintext.
2. Otherwise initialize the sealed store now: load or create the key, import a legacy
   `vault.json` (sealed entries win), delete the legacy file and write `vault.sealed`.
3. If that initialization fails (no Secret Service on the session bus, prompt dismissed,
   unsupported platform), keep using the plaintext `vault.json` exactly as before and
   retry on the next start.

Recovery: if the key entry is missing while `vault.sealed` exists, or the key no longer
decrypts the file, the file is renamed to `vault.sealed.unreadable` and an empty vault is
started; the user signs in again. The renamed file is kept in case the key returns.

## Observability

Startup records `credentialBackend` (`os_store` or `local_file`) in the `credentials`
phase of the diagnostics log; both values were added to the privacy allowlist. A
`local_file` fallback also emits a tracing warning with the store error.

## Validation

- Unit tests with an in-memory key source: round trip with no plaintext on disk, a
  16 KiB session, legacy import, fallback only before a sealed vault exists, and
  set-aside on a changed key.
- An ignored test (`cargo test -p dm-credentials -- --ignored`) uses the real OS store;
  it passed against GNOME Keyring.
- `cargo clippy -p dm-credentials --all-targets -- -D warnings` passes for
  `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, with the Windows and Apple stores
  selected respectively.
- Debug app on Linux: a plaintext vault was migrated to `vault.sealed` with the key in
  GNOME Keyring; with an unreachable session bus the app started on `local_file`.

Not yet verified: runtime behavior on Windows and macOS, KWallet as the Secret Service
provider, and the macOS Keychain access prompt after an update changes the ad-hoc
code signature.
